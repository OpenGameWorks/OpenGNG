# CodeWarrior idioms: Classes, constructors and virtuals

Constructors, destructors, new/delete, virtual calls and member layout. Each entry pairs an asm pattern seen in the original with the source that produces it, and names the function that proved it.

- A by-value class parameter the original uses in place (no byte-copy loop into the frame) belongs to a non-POD class: give a placeholder class `T() {}` and `T(const T &);` declarations.
- A `delete p` that tests `p` twice (`beqz a0; nop; beqz a0; nop; jal __dl__FPv; nop`) deletes a class with an inline empty destructor: declare `~T() {}` in the class (`EntityBaseClass` dtor, `Physics`).
- A `new T(...)` whose inline ctor stores go through a stack slot (`daddu s4,v0; sw s4,0x8C(sp)` after `jal __nw__FUi`, then `lw v0,0x8C(sp)` before each store) is an inline ctor with its own spilled `this`: `void *node; if ((node = __nw__FUi(n)) != 0) { char *volatile pThis = (char *)node; *(T **)node = __vt__Base; *(int *)(pThis + 4) = 0; ...; node = pThis; }`. The first vtable store goes through the raw pointer (`GameHud::SetNumber`, `EffectAPI::CreateMotionBlurEffect`). A vtable store names the bare symbol (`__vt__6PMNode`); the `0xE00`/`0x970` in the `%lo` is the symbol's own offset, so an added `+ 0xE00` is wrong (`ClockworkPuncher::AttachDamageMesh`, `PMNode::LoadBone`).
- A ctor whose original spills `this` at entry (`sw a0,N(sp)`) and reloads it before each member access takes a volatile parameter: `extern "C" Cls *__ct__NCls...(Cls *volatile pThis, ...) { ... pThis->m_x = 0; return pThis; }` (PFireTexture, PParticleSystem, PTextureManager, EffectAPI ctors).
- Inlined base-class ctors each spill their own `this` to a separate stack slot (e.g. 0x24/0x28/0x2C) from one load: write a nested block per base level, `{ unsigned char *pRaw = (unsigned char *)pThis; unsigned char *volatile pMesh = pRaw; { unsigned char *volatile pBase = pRaw; *(unsigned char **)pRaw = __vt__Base; ... } *(unsigned char **)pMesh = __vt__Mid; ... }`; the first vtable store goes through the raw pointer (PSkeleton, PMeshNode ctors). Inline member-object ctors (one `this` load, then several stores) take a plain `char *h = (char *)pThis + off;` block (Interface ctor).
- Do not alias a volatile `pThis` into a plain local (`char *base = (char *)pThis;`): the original reloads per access. `new X(...)` is `void *p = __nw__FUi(n); if (p) p = ctor(p, ...); pThis->m = p;`. `ASSERT(!"msg")` is `(!"msg") ? (void)0 : CdsAssert(...)`.
- A destructor whose implicit `__dt__6PArrayFv` (or other subobject) call passes `a1 = -1` destroys a data member, not a base: MWCC passes 0 to base-class destructors and -1 to member destructors. Declare `PArray m_array;` at offset 0 instead of `: public PArray` (`PShadowBuffer`, `PShadowVolume`).
- A ctor that spills `this` to `0x1C(sp)` and reloads it before stores needs a member sub-object with an empty user-declared destructor.
- `daddu s1,v0; beqz s1; daddu a0,s1; jal ctor; nop; daddu s1,v0` is `T *p = (T *)__nw__FUi(n); if (p != 0) { p = __ct__...(p); }`, a single pointer (`PParticleManager::CreateFrozenFx`).
- A list a class owns at a fixed offset is a real `PArray` member, not a `char[0x10]` placeholder cast to a pointer: the cast makes MWCC keep `&cursor` in a saved register. The member also produces the implicit ctor/dtor calls (`PObjectDisplayList::Destroy`, its ctor).
- A null-guarded virtual call through vtable offset 8 with `a1 = 1` (`lw t9,0(p); lw t9,8(t9); jalr; li a1,1`) is `delete p;` on a class with a virtual destructor. Drop the explicit `if (p != 0)`; `delete` emits the guard (`PMNode::DestroyChildren`).
- A ctor that calls `sceVu0UnitMatrix(this+off)` before other member ctors has an identity-matrix member at `off` (`CameraDebugMat` in `CameraDebug.h`); member ctors run in declaration order, so the call order fixes the layout.
- A destructor `__dt__8CEifFileFv` is a real `CEifFile::~CEifFile() { Cleanup(); }`: CodeWarrior emits the null test, the `short` delete flag and the `__dl__FPv` call itself. An `extern "C"` function spelling out that logic reproduces the bytes without the source (`src/game/CEifFile.cpp`). A derived class declares its base (`class LiftOperator : public EntityBaseClass`) and `virtual ~LiftOperator();`; the empty body `LiftOperator::~LiftOperator() {}` then emits the vtable store and the base destructor call (`src/game/LiftOperator.cpp`). The derived constructor names its base in a mem-initializer, `Rain::Rain() : EntityBaseClass((LoadClass)5, 0) { EnableSleep(false, false); }`: CodeWarrior then spills `this` to `0x1C(sp)` and stores the vtable once after the base call, as the original does; an `extern "C"` base-ctor call stores the vtable twice. The body never stores the vtable itself: an explicit `*(void **)this = __vt__X;` adds the `this` spill and a cleanup difference to a ctor the original keeps in `s0` (`WoodenChest::WoodenChest` in `src/game/WoodenChest.cpp`).
- A member whose original returns a value while your header declares it `void` gets the corrected return type in your header (`int NextBatch();`); an `extern "C"` function carrying the mangled name is never a substitute for the member definition.
- A constructor that stores `this` to `0x1C(sp)` and reloads it before each store has a member subobject whose type declares a destructor; CodeWarrior keeps `this` in `s0` when no member type has one. Such members are embedded as real classes (`#include "PArray.h"`, `PArray m_unk70;`) so the compiler constructs them implicitly; a manual `__ct__6PArrayFv(...)` call reproduces neither the spill nor the call order. A declared base destructor (`~PParticleSystem();`) gives derived constructors the same spill and makes derived destructors call it implicitly, so no explicit `__dt__` call appears in the body. A second spill slot holding `this+N` before two inline-ctor calls (`sceVu0UnitMatrix` at `this+0x40`, then at `slot+0x40`) is a nested aggregate member `struct { PMat4 a; PMat4 b; } m_unk40;` whose members have an inline constructor, not two separate members.
- `__nw__FUi(size)`, a null test and a constructor call on the result are one `p = new X;` expression. A class shell with the constructor and the size (`class X { public: X(); char _pad[0x290]; };`) is enough; spelling out the three calls schedules the branches differently (`SpawnEntity` in `src/game/EntityAllocator.cpp`).
- `lw t9,0(a0); lw t9,N(t9); jalr t9` is a C++ virtual call; a cast function-pointer call loads `v0` instead. CodeWarrior vtables start with an 8-byte header, so slot `N` is virtual number `(N - 8) / 4` in declaration order, the virtual destructor taking one slot. A class declaring virtuals up to that slot (`.venv/bin/python tools/vtable.py CLASS < /dev/null` lists each slot's target) and a cast `((View *)this)->Method(args)` reproduce it; `src/game/ClockworkMaximo.cpp` shows one.
- An embedded subobject reached through a cast `(T *)((char *)this + N)` is computed once into a saved register; a member array `char m_unkN[size];` used as `(T *)m_unkN` is recomputed (`addiu a0,s0,N`) before each call, as the original usually does (FontManager::Init in `src/game/Font.cpp`).
- An inlined derived-class `new` whose original loads a later base's vtable high half (`lui v1,__vt__6PMNode`) before the two `this` spills is the real inline-ctor chain, which the `char *volatile pThis` spelling cannot schedule: shells `class PResource { PResource() { m_unk4 = 0; } virtual ~PResource(); int m_unk4; };`, `class PMNode : public PResource { PMNode() { InitMembers(); } ... PArray m_unk14; ... PMNodeMatrix m_unk40; ... PArray m_unkD8; };` (`PMNodeMatrix() { sceVu0UnitMatrix(m); }`), `class PMeshNode : public PMNode { PMeshNode() { InitMembers(); } ... PArray m_unk130; };` with `PArray();` declared, then `p = new PMeshNode;` (`PCutScenePlayer::AttachActors`). No `__ct__` symbol exists for these classes, so every construction site in the executable inlines them.
